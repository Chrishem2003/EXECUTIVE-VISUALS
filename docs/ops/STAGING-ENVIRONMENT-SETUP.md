# Executive Visuals staging environment setup

This guide configures the protected GitHub Actions `staging` environment. It does not change Render, Supabase, Neon, production, payment live mode or customer data.

## Where to configure

Open the repository on GitHub → **Settings → Environments → staging**. Add secrets under Environment secrets and non-secret values under Environment variables. Restrict environment reviewers to the repository owner/reviewers. Never paste secret values into PRs, source code, chat or logs.

The approved staging Supabase project is `Chrishem Platform Staging`, ref `bokxljngydmqrmktofwm`, URL `https://bokxljngydmqrmktofwm.supabase.co`. The storage, worker and backup scripts reject other project refs. This is the existing shared staging project, not a dedicated production data plane.

## Required GitHub environment secrets

| Secret | Where to obtain it / purpose |
|---|---|
| `SUPABASE_STAGING_URL` | Supabase → Project Settings → API. Exact URL above. |
| `SUPABASE_STAGING_ANON_KEY` | Supabase → Project Settings → API Keys. Use the publishable key or legacy anon key for client-authenticated storage tests. |
| `SUPABASE_STAGING_SECRET_KEY` | Supabase → Project Settings → API Keys. Server-only secret key (or supported service-role key); never expose in browser code. |
| `SUPABASE_STAGING_DB_URL` | Supabase → Project Settings → Database → Connection string. Use the staging project's direct connection or its pooler URL; the host/username must identify this project. |
| `STORAGE_TEST_OWNER_EMAIL` | Email of a disposable staging-only Supabase Auth user that owns the test path. |
| `STORAGE_TEST_OWNER_PASSWORD` | Strong password for that disposable owner account. |
| `STORAGE_TEST_OTHER_EMAIL` | Email of a second, distinct disposable staging-only Supabase Auth user. |
| `STORAGE_TEST_OTHER_PASSWORD` | Strong password for the second account. |
| `STAGING_BACKUP_ENCRYPTION_PASSPHRASE` | Generate a unique random passphrase of at least 24 characters. Keep it separately from backup artifacts. |
| `PADDLE_SANDBOX_API_KEY` | Paddle **Sandbox** developer API key only; the validator requires the sandbox marker `_sdbx_`. |
| `PADDLE_WEBHOOK_SECRET` | Endpoint secret key generated by the Paddle Sandbox notification destination described below. This is not the Paddle API key. |
| `PESAPAL_SANDBOX_CONSUMER_KEY` | Pesapal QA/Sandbox merchant consumer key. |
| `PESAPAL_SANDBOX_CONSUMER_SECRET` | Pesapal QA/Sandbox merchant consumer secret. |
| `OPS_ALERT_WEBHOOK_URL` | HTTPS incoming webhook URL from your chosen alert destination. The monitor sends a JSON payload with a `text` field. |

The storage acceptance scripts authenticate these two test accounts at runtime using Supabase's password grant and hold the returned access tokens in memory. This avoids long-lived, expiring JWT secrets. Do not use your personal account or any production account. Create two disposable users in the staging project's Auth Users screen and set `STORAGE_TEST_OWNER_ID` to the first user's UUID.

## Optional runtime acceptance switch

Add the GitHub environment variable `STAGING_RUNTIME_TESTS_ENABLED` with value `true` only after the strict preflight reports READY and you have reviewed the test identities and staging target. Leave it unset or `false` during setup.

When enabled, same-repository pull requests authored by `Chrishem2003` can automatically run the safe staging-only checks:
- Private storage: upload one random object, verify owner access and cross-tenant denial, then delete it.
- Worker restart: write synthetic heartbeat records and test child-process recovery.
- Payment provider: Paddle Sandbox read-only credential check and Pesapal Sandbox token/IPN verification.

This switch does **not** enable the encrypted backup export or synthetic monitoring alert. Those remain manual because they create an encrypted artifact or send an external notification. Fork pull requests never receive staging secrets. The strict preflight remains a separate required gate.

## Paddle Sandbox notification destination

Create this in the **Paddle Sandbox** account, not the Live account:

- Dashboard: **Events → Notifications → New destination**
- Description: `Executive Visuals Staging — Paddle subscription webhook`
- Notification type: **URL**
- URL: `https://executive-visuals-cloud-staging.onrender.com/api/webhooks/paddle`
- Usage type: **All** (platform and simulation events), so the sandbox webhook simulator can test delivery.
- Subscribe to the event types supported by the current server handler:
  - `subscription.created`
  - `subscription.activated`
  - `subscription.updated`
  - `subscription.canceled`
  - `subscription.past_due`
  - `subscription.paused`
  - `subscription.resumed`
  - `transaction.completed`
  - `transaction.payment_failed`
  - `adjustment.created`
  - `adjustment.updated`

Save the destination, then copy its **endpoint secret key** into GitHub's `PADDLE_WEBHOOK_SECRET` environment secret. Each destination has its own endpoint secret; do not substitute the Paddle API key. Use Paddle's simulator for a test event before enabling checkout. The application route verifies the `Paddle-Signature` header and stores idempotent webhook events.

Paddle's documentation: [Create notification destinations](https://developer.paddle.com/webhooks/about/notification-destinations/) and [Verify webhook signatures](https://developer.paddle.com/webhooks/about/signature-verification/).

## Pesapal Sandbox IPN destination

In the Pesapal Sandbox merchant account, register the HTTPS callback URL exactly as shown above. Copy the returned `ipn_id` UUID to `PESAPAL_IPN_ID`. The server route is a GET IPN endpoint; do not use a frontend return URL in place of this callback. The acceptance script verifies that the configured IPN ID and callback URL are registered to the same sandbox merchant.

## Safety and execution

- The preflight prints only missing/invalid names and readiness state, never credential values.
- Strict launch preflight must report `READY`; `BLOCKED` or `INVALID` fails the readiness check.
- Storage tests upload one small random object, verify owner read, deny cross-user read, verify signed read and delete the object in cleanup.
- Worker acceptance writes only synthetic heartbeat rows in the approved staging project and exercises local child-process crash/restart; it does not deploy a Render worker or submit paid provider jobs.
- Encrypted backup acceptance exports the approved staging database schema and private bucket only. It does not include `auth.users`; restore requires a reviewed identity reconciliation plan.
- Payment credential acceptance calls Paddle Sandbox GET endpoints and Pesapal Sandbox token/IPN-list endpoints only. It does not create checkout, register a new IPN, or charge a payment method.
- Keep `PADDLE_ALLOW_LIVE=false`, `PESAPAL_ALLOW_LIVE=false` and `PADDLE_PESAPAL_BILLING_ENABLED=false` until the complete sandbox checkout/webhook/reconciliation matrix passes.
- Never use production JWTs, service keys, database URLs, payment credentials or customer media in staging acceptance.
